## 2. 3개 LLM 호출 시점과 역할

### 2.1 실시간 인터뷰 (v9.1)

- **시점:** 세션 진행 중 매 턴
- **프롬프트:** `회상치료_실행_프롬프트_v9.1.md` 전문을 system prompt로
- **입력:** elderlyProfile + sessionState + 어르신 발화
- **출력:** speech, action, responsePattern, questionType, mentionedEntities 등 (JSON)
- **특징:** Structured Output API 사용 필수. 출력 스키마는 v9.1 "출력 형식" 섹션 참조.

### 2.2 세션 기록 정리 (v4.1)

- **시점:** 세션 종료 직후, 1회 호출
- **프롬프트:** `회상치료_세션기록_실행_프롬프트_v4.1.md` 전문을 system prompt로
- **입력:** elderlyProfile + sessionDate + conversationLog(전체) + finalSessionState
- **출력:** nextSessionPrep + dataPipeline (JSON)
- **특징:** 대화 로그 전체를 넣으므로 토큰 사용량이 큼. 한 세션당 1회만 호출.

### 2.3 보호자 리포트 생성 (v2.1)

- **시점:** v4.1 처리 완료 후
- **프롬프트:** `보호자_리포트_생성_프롬프트_v2.1.md` 전문을 system prompt로
- **입력:** elderlyName, sessionNumber, sessionDate, guardianName, guardianRelation, nextSessionPrep(v4.1 출력), conversationLog, sensitiveFilter, sessionDurationMinutes, totalTurns
- **출력:** guardianReport (JSON)
- **특징:** sensitiveFilter는 v4.1의 dataPipeline.sensitiveContent 중 guardianReportFilter=true인 항목에서 추출.

## 3. 세션 엔진 — 구현 스펙

### 3.1 세션 시작

1. DB에서 elderlyProfile 로드 (이전 세션의 familyStatusUpdates, tabooTopics, previousSessionSummary 반영 완료 상태)
2. sessionState 초기화:

```json
{
  "turnCount": 0,
  "elapsedMinutes": 0,
  "topicTurnCount": 0,
  "currentPersonTurnCount": 0,
  "currentPerson": null,
  "deathMentionCounter": 0,
  "discomfortCounter": 0,
  "sessionPhase": "main",
  "blockedPatterns": [],
  "blockedQuestionTypes": [],
  "recentPatterns": [],
  "recentQuestionTypes": [],
  "eTypeCount": 0,
  "bestQuestionCount": 0,
  "emotionStructureCount": 0,
  "treasureDetected": false,
  "sttLowConfidenceWords": [],
  "sttGarbageDetected": false,
  "currentScene": null,
  "sceneTurnCount": 0,
  "sceneMaxReached": false,
  "refusalCount": 0,
  "consecutiveRefusals": 0,
  "conversationMode": "EXPLORE",
  "recentScenes": [],
  "currentLifePeriod": null,
  "lifePeriodTurnCount": 0,
  "lifePeriodMaxReached": false,
  "allowedActions": null,
  "forcedTransitionTarget": null
}
```

3. 첫 호출: sessionState + elderlyProfile → LLM → 오프닝 발화 생성

**⚠️ 첫 턴 특수 처리:**
- 첫 턴은 어르신 발화가 없는 상태로 LLM을 호출한다. `elderlyUtterance`를 빈 문자열("")로 넘기면 LLM이 오프닝 인사를 생성한다.
- 첫 턴에서는 엔진 전처리(보물 키워드 스캔, STT 처리)를 **건너뛴다** — 스캔할 어르신 발화가 없으므로.
- turnCount는 첫 턴에서 0→1로 증가. 카운터 갱신은 정상 진행하되, 어르신 발화 기반 판정(거부 감지, 보물 매칭)은 스킵.

### 3.2 매 턴 처리 루프

```
어르신 발화 (STT) → 엔진 전처리 → LLM 호출 → 엔진 후처리 → TTS 재생
```

#### 3.2.1 엔진 전처리 (LLM 호출 전)

| 항목 | 처리 내용 |
|------|----------|
| STT 신뢰도 | 단어별 confidence score를 sttLowConfidenceWords에 주입 (0.8 미만 단어) |
| STT 오염 감지 | "자막제작 by", "유료광고 포함", 동일 구절 3회+ 반복 감지 → sttGarbageDetected=true |
| 시간 갱신 | elapsedMinutes = (현재시각 - 세션시작시각) / 60 |
| 보물 매칭 | 어르신 발화에서 보물 키워드 스캔 → treasureDetected 갱신 (아래 3.3 참조) |

#### 3.2.2 엔진 후처리 (LLM 응답 수신 후)

LLM 응답 JSON을 파싱하여 다음 턴의 sessionState를 갱신:

| 필드 | 갱신 로직 |
|------|----------|
| turnCount | +1 |
| topicTurnCount | LLM의 currentTopic이 이전과 같으면 +1, 다르면 1로 리셋 |
| currentPersonTurnCount | LLM의 mentionedEntities.people에서 주요 인물 추출. 같은 인물이면 +1, 다르면 1로 리셋 |
| currentPerson | 현재 대화 대상 인물 갱신 |
| deathMentionCounter | 어르신 발화에서 죽음 관련 언급 감지 시 +1 |
| discomfortCounter | LLM의 riskLevel이 "medium" 이상이면 +1 |
| recentPatterns | LLM의 responsePattern을 append. 최근 3개 유지 |
| recentQuestionTypes | LLM의 questionType을 append. 최근 3개 유지 |
| blockedPatterns | recentPatterns에서 3연속 동일 패턴 계산 → 해당 패턴 block |
| blockedQuestionTypes | recentQuestionTypes에서 3연속 동일 계산 → 해당 유형 block |
| eTypeCount | LLM의 questionType이 "E"이면 +1. 4 이상이면 "E"를 blockedQuestionTypes에 추가 |
| bestQuestionCount | LLM의 speech에 "제일~한 건?" 패턴 포함 시 +1 |
| emotionStructureCount | LLM의 speech에 "어떤 마음/기분/느낌" 패턴 포함 시 +1 |
| currentScene | LLM의 currentScene 값으로 갱신 |
| sceneTurnCount | 같은 scene이면 +1, 다르면 1로 리셋 |
| sceneMaxReached | sceneTurnCount >= 3이면 true |
| recentScenes | currentScene을 append. 최근 5개 유지 |
| refusalCount | 어르신 발화가 거부 표현이면 +1 |
| consecutiveRefusals | 거부면 +1, 비거부면 0으로 리셋 |
| currentLifePeriod | LLM의 currentTopic + currentSubtopic에서 인생 시기 추출 |
| lifePeriodTurnCount | 같은 시기면 +1, 다르면 1로 리셋 |
| lifePeriodMaxReached | lifePeriodTurnCount >= 8이면 true |
| conversationMode | 아래 3.4 참조 |
| sessionPhase | 아래 3.5 참조 |

#### 3.2.3 거부 표현 감지 키워드

엔진이 어르신 발화에서 스캔할 거부 표현:
"없어", "모르겠어", "됐어", "기억 안 나", "글쎄", "별로", "딱히", "그건 모르겠다"

**"이해가 안 돼" ≠ 거부.** "무슨 말이야?", "이해가 안 돼", "뭘 물어보는 거야?" 등은 거부가 아닌 질문 난이도 문제. refusalCount 증가 없음.

### 3.3 보물 키워드 매칭

어르신 발화에서 아래 키워드를 스캔. 매칭 시 `treasureDetected=true`.

**명시적 (12개):**
"아직도 생각나", "그게 마지막", "보고 싶", "꿈에 나와", "그때 그랬어야", "못 해줬", "그게 한이야", "지금 생각하면", "나중에야 알았", "그때부터 달라졌", "평생 잊을 수", "세상이 무너진"

**암묵적 (8개):**
"지금도 그 맛이 안 나", "요즘은 그런 게 없", "그때는 달랐", "거기서만", "아무 데서도 못", "그 사람만큼은", "그냥 ~가 아니라", "단순한 ~가 아니"

**말끝 흐림 패턴:**
"그게 참...", "그러니까...", (발화 끝이 "..."로 끝나며 감정어 동반)

키워드 매칭은 부분 매칭(contains) 방식. "보고 싶"은 "아빠가 보고 싶지"에서도 매칭.

### 3.4 대화 흐름 모드 (conversationMode)

| 모드 | 진입 조건 | LLM 행동 |
|------|----------|----------|
| EXPLORE | 기본값. SHIFT 후 자동 복귀 | 넓게 탐색. 한 장면 2턴 이하 |
| FOCUS | 어르신 답변 ≥30단어 + 감정어/디테일 포함 | 깊이 진입. 같은 장면 최대 3턴 |
| SHIFT | 거부 1회 이상 또는 discomfortCounter 2 이상 | 완전 전환. 전환 후 EXPLORE로 복귀 |

엔진이 매 턴 판정하여 conversationMode에 세팅. LLM은 이 값을 읽고 행동 조절.

### 3.5 세션 페이즈 판정 (sessionPhase) — 핵심

턴 기반 + 시간 기반 이중 제한. **먼저 도달하는 쪽 적용.**

| 인지 수준 | 턴 soft/hard | 시간 soft/hard |
|-----------|-------------|---------------|
| normal | 20/25 | 25분/30분 |
| MCI | 15/18 | 20분/25분 |
| moderate | 10/12 | 15분/20분 |

```
if turnCount >= hard_cap OR elapsedMinutes >= hard_time:
    sessionPhase = "force_end"
elif turnCount >= soft_cap OR elapsedMinutes >= soft_time:
    if minimumQualityMet:  # 아래 3.6 참조
        sessionPhase = "wrapup"
    else:
        sessionPhase = "main"  # 품질 미달이면 좀 더 진행
elif earlyTerminationCondition:  # 아래 3.6 참조
    sessionPhase = "wrapup"
else:
    sessionPhase = "main"
```

- `wrapup`: LLM이 2~3턴 마무리 시퀀스 진행
- `force_end`: LLM이 즉시 마무리 발화 후 종료

### 3.6 최소 품질 기준 + 조기 종료 (신규 스펙)

#### 최소 품질 기준 (minimumQualityMet)

soft cap 도달 시, 아래 조건을 **모두** 충족해야 wrapup 허용:
1. 어르신 총 발화 시간 ≥ 3분 (totalElderlyUtteranceSec ≥ 180)
2. 어르신 발화 중 20단어 이상 답변 ≥ 2회
3. treasureDetected가 세션 중 최소 1회 true (보물 키워드 매칭 기록으로 판정. keyMemory는 v4.1 후처리에서 생성되므로 세션 중 측정 불가 — treasureDetected만 기준)

**미달 시:** sessionPhase를 "main"으로 유지. 단, hard cap에서는 무조건 종료.

#### 조기 종료 조건 (earlyTerminationCondition)

soft cap 미도달이어도 아래 조건에서는 wrapup 진입:
1. consecutiveRefusals ≥ 5
2. discomfortCounter ≥ 3
3. riskLevel이 "high"로 2턴 연속
4. 어르신이 종료 신호 발화 ("끝내자", "그만하자", "더 물어보지 마" 등)

4번(어르신 종료 신호)의 경우 sessionPhase="force_end" 직접 세팅. LLM의 절대 규칙 #7이 작동.

### 3.7 allowedActions 제한 (엔진 → LLM 강제)

특정 상황에서 LLM의 action 선택을 서버가 제한:

```json
// 예: wrapup 진입 시
"allowedActions": ["end", "cooldown", "listen"]

// 예: force_end 시
"allowedActions": ["end"]

// 예: 보물 감지 시 (전환 방지)
"allowedActions": ["deepen", "listen", "listen_more", "continue"]
```

allowedActions가 null이 아니면, LLM은 해당 리스트의 action만 사용 가능 (절대 규칙 #5).

### 3.8 familyStatus 파이프라인

```
LLM 응답의 mentionedEntities.people[].aliveStatus
    ↓ (엔진이 수집)
세션 종료 후 v4.1 호출 → familyStatusUpdates 생성
    ↓ (엔진이 처리)
elderlyProfile.familyStatus 자동 업데이트
    ↓
다음 세션에서 절대 규칙 #6 (사망 부모 현재형 금지) 자동 반영
```

**충돌 처리:** 기존 alive=false인데 새로 alive=true로 나오면 → flag 생성, 수동 검증.

## 4. API 호출 흐름 — 턴 단위 상세

```
1. 어르신 발화 → STT 변환
2. 엔진 전처리:
   - STT 신뢰도/오염 판정
   - 보물 키워드 스캔
   - elapsedMinutes 갱신
   - sessionState에 위 결과 반영
3. LLM API 호출:
   - system: v9.1 프롬프트 전문
   - user: {
       "elderlyProfile": {...},
       "sessionState": {...},
       "elderlyUtterance": "어르신 발화 텍스트",
       "sttConfidence": 0.87
     }
   - response_format: Structured Output (v9.1의 출력 JSON 스키마)
4. LLM 응답 수신 + JSON 파싱
5. 엔진 후처리:
   - 카운터 갱신 (3.2.2 참조)
   - sessionPhase 판정 (3.5 참조)
   - conversationMode 판정 (3.4 참조)
   - 대화 로그 DB 저장
6. speech → TTS 변환 → 재생
7. 다음 턴 대기
```

### 4.1 LLM API 호출 코드 예제 (Claude)

```javascript
// Node.js + Anthropic SDK 예제
import Anthropic from '@anthropic-ai/sdk';
import fs from 'fs';

const client = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

// v9.1 프롬프트를 파일에서 로드
const systemPrompt = fs.readFileSync('./prompts/v9.1.md', 'utf-8');

// 실시간 인터뷰 — 매 턴 호출
async function callInterviewLLM(elderlyProfile, sessionState, elderlyUtterance, sttConfidence) {
  const userMessage = JSON.stringify({
    elderlyProfile,
    sessionState,
    elderlyUtterance,
    sttConfidence
  });

  const response = await client.messages.create({
    model: 'claude-sonnet-4-20250514',
    max_tokens: 1024,
    system: systemPrompt,
    messages: [{ role: 'user', content: userMessage }]
  });

  // 응답 텍스트에서 JSON 파싱
  const content = response.content[0].text;
  const parsed = JSON.parse(content);
  
  return parsed;
  // parsed = { speech, tts_text, action, responsePattern, questionType, ... }
}
```

**Structured Output이란?**
LLM에게 "응답을 반드시 이 JSON 스키마에 맞춰 줘"라고 강제하는 API 기능. Claude API에서는 `tool_use`를 활용하거나, system prompt에 JSON 스키마를 명시하고 응답을 파싱하는 방식을 사용한다. 핵심은 **LLM 응답이 항상 파싱 가능한 JSON으로 나오도록 보장**하는 것.

```javascript
// 방법 1: system prompt에 스키마 명시 (간단, PoC 추천)
// → v9.1 프롬프트의 "출력 형식" 섹션이 이미 JSON 스키마를 정의하고 있음
// → LLM 응답을 JSON.parse()로 파싱. 실패 시 재호출.

// 방법 2: Claude tool_use 활용 (더 엄격)
const response = await client.messages.create({
  model: 'claude-sonnet-4-20250514',
  max_tokens: 1024,
  system: systemPrompt,
  messages: [{ role: 'user', content: userMessage }],
  tools: [{
    name: 'interview_response',
    description: '인터뷰 응답을 구조화된 형식으로 반환',
    input_schema: {
      type: 'object',
      properties: {
        speech: { type: 'string', description: '어르신에게 할 발화' },
        tts_text: { type: 'string', description: 'TTS용 텍스트' },
        action: { type: 'string', enum: ['continue', 'deepen', 'shift', 'listen', 'end'] },
        responsePattern: { type: 'string' },
        questionType: { type: 'string' },
        mentionedEntities: { type: 'object' },
        currentTopic: { type: 'string' },
        currentSubtopic: { type: 'string' },
        riskLevel: { type: 'string', enum: ['low', 'medium', 'high'] }
      },
      required: ['speech', 'tts_text', 'action']
    }
  }],
  tool_choice: { type: 'tool', name: 'interview_response' }
});

// tool_use 응답에서 input 추출
const toolBlock = response.content.find(b => b.type === 'tool_use');
const parsed = toolBlock.input;
// → 스키마에 맞는 JSON이 보장됨
```

**PoC 권장:** 방법 1로 시작. JSON 파싱 실패율이 높으면 방법 2로 전환.

### 4.2 에러 처리

| 상황 | 처리 |
|------|------|
| LLM 응답 timeout | 재호출 1회. 실패 시 마지막 유효 턴의 suggestedQuestions[0]을 speech로 사용 |
| JSON 파싱 실패 | 재호출 1회. 실패 시 마지막 유효 턴 메타데이터 유지 + 기본 질문 |
| 필수 필드(speech) 누락 | speech만 있으면 TTS 전달. 나머지는 마지막 유효값 |
| STT 완전 실패 | "잘 안 들렸어요, 한 번 더 말씀해주시겠어요?" 고정 발화 |

## 5. 세션 종료 후 처리 흐름

```
세션 종료 (sessionPhase="force_end" 또는 어르신 종료)
    ↓
1. 전체 conversationLog 구성 (모든 턴의 role + text + structured + audioFeatures)
    ↓
2. v4.1 LLM 호출 → nextSessionPrep + dataPipeline 생성
    ↓
3. dataPipeline.sensitiveContent에서 guardianReportFilter=true 추출 → sensitiveFilter 구성
    ↓
4. v2.1 LLM 호출 → guardianReport 생성
    ↓
5. DB 저장:
   - nextSessionPrep → 다음 세션 참조용
   - dataPipeline → 데이터 분석용
   - guardianReport → 보호자 앱 전달용
    ↓
6. elderlyProfile 업데이트:
   - familyStatusUpdates → familyStatus merge
   - avoidInNextSession → tabooTopics 누적
   - nextSessionLeads → previousSessionSummary 주입
   - entityGraph → 엔티티 DB merge
    ↓
7. 보호자 앱에 리포트 알림 전송
```

## 6. 보호자 피드백 수집 구조

### 6.1 리포트 하단 액션 버튼 (프론트엔드)

보호자 리포트 JSON을 앱에 렌더링한 뒤, 하단에 다음 버튼 배치:

1. **"이 이야기 더 듣고 싶어요"** → 해당 keyMemory의 ID와 함께 저장
2. **"내용 정정/보충하기"** → 자유 텍스트 입력 폼
3. **"가족에게 공유하기"** → 공유 기능 (카카오톡 등)
4. **"다음에 물어봐 주세요"** → 자유 텍스트 입력 → nextSessionLeads에 추가

### 6.2 피드백 데이터 활용

```
보호자 피드백
    ↓
guardianFeedback DB 테이블에 저장:
{
  "sessionId": "...",
  "feedbackType": "want_more | correction | share | suggest_topic",
  "linkedMemoryId": "MEMORY_001" (optional),
  "freeText": "..." (optional),
  "timestamp": "..."
}
    ↓
다음 세션 준비 시:
- want_more → nextSessionLeads priority 상향
- correction → facilitatorNotes에 추가 + 필요 시 elderlyProfile 수정
- suggest_topic → nextSessionLeads에 신규 항목 추가
```

### 6.3 PoC 단계 최소 구현

PoC에서는 **1번(더 듣고 싶어요)과 4번(다음에 물어봐주세요)만 구현해도 충분.** 이 두 개가 보호자 참여율 측정의 핵심 지표. 2, 3번은 후순위.

## 8. STT/TTS 연동

### 8.1 STT (음성→텍스트)

- 한국어 STT API 사용 (Google Cloud Speech / Whisper 등)
- 단어별 confidence score 필수 출력
- 어르신 발화 종료 감지: 2~3초 침묵 → 발화 종료로 판정
- audioFeatures 추출:
  - **PoC 필수:** durationSec (발화 길이), silenceSec (침묵 길이) — STT API에서 자동 제공
  - **후순위 (PoC에서 미구현 가능):** laughDetected, cryDetected (별도 오디오 분류 모델 필요), speechRate (발화속도, 단어수/초 계산으로 대체 가능)

### 8.2 TTS (텍스트→음성)

- LLM 응답의 `tts_text` 필드 사용 (speech와 별도로 TTS 최적화된 텍스트)
- 한 문장 30자 이내 (v9.1 규칙). TTS 한 호흡 단위.
- 여성 음성, 따뜻한 톤, 적당한 속도

## 10. 주의사항

### 10.1 절대 지켜야 할 것

1. **v9.1의 절대 규칙 7개는 엔진에서도 이중 방어.** 특히 #1(인물 7턴), #4(시기 8턴)은 엔진이 카운터로 강제. LLM이 무시하더라도 엔진의 allowedActions로 전환 강제.
2. **사망 부모 현재형 금지 (#6)는 familyStatus 파이프라인이 정상 작동해야 한다.** familyStatusUpdates → familyStatus merge가 안 되면 다음 세션에서 같은 위반 반복.
3. **종료 후 질문 금지 (#7)는 엔진이 sessionPhase="force_end" + allowedActions=["end"]로 강제.**
4. **sensitiveContent의 guardianReportFilter=true 항목은 보호자 리포트에 절대 노출 금지.**

### 10.2 흔한 실수

1. sessionState의 카운터를 LLM에게 갱신하게 하는 것 → LLM은 읽기만. 엔진이 갱신.
2. 보물 키워드를 LLM이 판정하게 하는 것 → 엔진이 키워드 매칭, treasureDetected로 전달.
3. v4.1 호출 시 conversationLog를 일부만 넣는 것 → 전체 대화 로그 필수. 누락 시 후반부 커버 실패.
4. v2.1 호출 시 sensitiveFilter를 빈 배열로 넣는 것 → v4.1의 sensitiveContent에서 추출 필수.
